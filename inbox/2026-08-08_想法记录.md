# 想法记录

最近用 Codex / Agent 做项目开发时，我越来越觉得“一个 Agent 从头到尾负责所有事情”不太理想。

主要矛盾是：

- 长上下文会越来越贵，而且容易出现上下文腐败；
- 频繁开新 Agent 又需要重新理解整个项目；
- 真正困难的往往不是写某一段代码，而是任务拆解、上下文交接、验收和保持全局一致性。

我想到一种工作流：

- 一个长期存在的主 Agent 负责掌握项目整体目标、当前状态、架构约束和任务优先级；
- 主 Agent 不直接承担所有实现，而是把具体开发任务整理成边界清楚的 prompt，交给短生命周期子 Agent；
- 子 Agent 只读取完成当前任务所需的局部上下文，完成代码、测试和说明后提交结果；
- 主 Agent 再负责 review 子 Agent 的产出，对照验收标准判断是否通过，并决定下一步；
- 重要的架构决策、接口约束和项目状态通过仓库文档持久化，而不是全部依赖某个 Agent 的聊天上下文。

我觉得这种方式可能同时缓解“长上下文成本高”和“新 Agent 不了解项目”的矛盾，但还没确定应该怎样划分主 Agent / 子 Agent 的权限，也没有想清楚失败重试、并行任务冲突、token 成本统计和自动验收应该放在哪一层。

后续如果继续做，我想把它发展成一套可复用的 Agent 驱动开发工作流，而不是只服务当前某一个项目。
